## 实机安装发现并处理的问题

旧 `mosey_pme110/product` 目录含挂载工具生成的链接。全量复制会带入无效嵌套链接，
现改为只导入校验过的四个 APK 和三个配置文件；最终暂存目录只保留挂载工具需要的分区链接。

旧 Stack 的卸载脚本会全局终止 `mosey_server`。迁移先保存原文件，再把旧清理脚本改名，
避免下一次启动移除旧模块时误杀新的原厂服务。重复安装保留第一次的干净备份。

## 1.1.1 当前会话接管与清理

按设备所有者要求，在保留本次临时 root 的情况下，将暂存模块切换到正式模块目录。
系统层文件内容逐一比对一致后，由合并模块重新绑定；安装桥接 1.1.1，LSPosed 启用和两个
作用域检查通过，后台保活切换到合并模块自身脚本。

实际发现 Android shellCommand 不能直接使用本模块私有日志文件作为输出 FD，命令报
`Failed transaction (2147483646)`。通过管道捕获 stdout/stderr 后再写日志，返回码恢复正常；
在真实后台守护中观察到缓存进程恢复成功，无需改变 SELinux 规则或日志文件权限。
新增回归检查验证管道 FD、stdout/stderr 及非零退出码保留。

旧模块、旧服务目录、下载的旧包与调试文件被清理。恢复资料移到 Mac，不作为手机上的旧模块
继续保留。部分旧系统文件仍是本次内核挂载的根，系统拒绝 unlink；将这些只读文件移入
`/data/adb/opairshare_pme110/retired-mounts`，不再列入模块列表。启动清理脚本会在没有挂载
引用后删除该缓存；当前有引用时保留，不强拆活跃挂载。

当前 boot 保持不变，热切换未主动结束收发进程。后续 Android exit-info 记录了 Mosey 的
`OTHER KILLS BY SYSTEM / o-kill(2)`，后台守护已恢复应用及缺失的原厂 daemon。
这验证了本次观察窗口内的恢复路径，不能据此宣称长期稳定或新传输已经完成。
**未因此补做整机冷启动验证。**

## 1.1.3 依赖遗漏回归与实际发送

用户报告清理后双方无法发现，诊断页面仍显示服务存在和接口 UP。实际日志明确记录：
OShare 在首次解析设备列表时因 `com.google.flatbuffers.FlatBufferBuilder` 类定义缺失失败。
先前构建只包含 DexKit 本体与 Kotlin，没有手工带入 FlatBuffers 传递依赖；旧符号缓存和
旧宿主进程会掩盖缺失。此缺陷属于本分支构建遗漏，不是 Wi-Fi 驱动缺失。

现显式固定依赖、检验最终 DEX 的类定义，并拒绝只有描述符引用却没有实现的 APK。
旧 1.1.1 产物检查失败，新产物通过；Android 上独立 app_process 实际运行两个无缓存
解析器，34 个设备列表角色、6 个分享入口角色及 8 个接收界面角色全部解析通过。
重启两个宿主应用后记录到新符号解析、接收宿主握手和真实 Mac target 更新，用户确认
双方均能发现。

用户随后报告发送及取消卡住，现场为 PrepareBestChannel、原生 Active Transfers=0、
桥接 busy=1。手机 `cmd wifi status` 同时证实 Wi-Fi 关闭。安装带现有会话复用检查的
实验修复并开启 Wi-Fi后，用户确认可用；发送记录为 1003 → 1005 → 1006，最终 100%。
桥接 busy 已回到 0。**不能从该次成功区分每项实验改动的贡献，也未证明取消重试回归通过。**

控制器协程恢复时允许空渠道参数，首版诊断钩子曾错误调用 null.equals；LSPosed 保护器
记录异常并回退原方法。发布源码改为常量集合.equals，保留原方法回退。用户确认成功后
不再重启或替换当前运行进程；这项空参数保护未在该运行进程中热加载。

仍有旧版可选钩子与 27391 不匹配的告警，后台发现、长时间恢复、取消等仍有验收边界。
保持 root、boot ID 和活跃驱动，未重启整机或关闭热点。
